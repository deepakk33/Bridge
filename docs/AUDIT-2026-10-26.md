# Audit — 2026-10-26

**Status**: Findings only. Nothing fixed, nothing committed beyond this doc and the backlog rows it spawned.
**Method**: Source review of both apps + the PRD and OpenSpec specs, then both apps built and driven on real hardware (MacBook Air M3 / macOS 26, Galaxy S25 / Android 16 One UI 8.5).
**Scope**: Whole product as shipped at `0.1.1`.

Each finding carries an evidence class:

| Class | Meaning |
|---|---|
| **RUNTIME** | Observed on the running app this session |
| **GREP** | Absence or presence proven by search (dead code, missing callers) |
| **SOURCE** | Read from code; behaviour inferred, not observed |
| **DOC** | Contradiction between docs/specs and code |

Findings are grouped into eleven work items (AUD-A … AUD-K), each sized to be one branch
and verifiable on real hardware. Backlog rows BR-2 … BR-12 mirror these one-to-one.

---

## Layman summary

Four things are true at once, and they compound.

**The Mac panel is broken by a single missing line.** It renders as an old-style menu
instead of a panel, which shreds the layout, greys out most of the text, kills the
file-drop target, and makes the pairing confirmation physically impossible to show. That
last one is why pairing was made automatic.

**The apps lie about the connection.** When the link dies quietly, the Mac keeps saying
"Connected" for up to two minutes and reports every failed send as a success. When the
phone's service is killed, the Mac blames distance — it says "Out of range" for a phone
sitting on the desk. The code that would tell the truth was written and never wired up.

**The security model in the docs does not exist in the code.** The README, the PRD,
CLAUDE.md and the OpenSpec specs all describe mutual TLS and a six-digit pairing code
confirmed on both screens. Neither was built. Pairing auto-accepts, the channel is
plaintext, and packets from a completely unidentified peer are processed.

**The headline feature is off and nobody is told.** Notification mirroring is deny-by-default
with an allow-list that starts empty, so on a fresh install nothing mirrors, forever, and
neither screen says so. On the test phone right now, zero apps are enabled.

## AUD-A — The Mac panel renders as an NSMenu, not a panel

**Severity**: High · **Platform**: mac · **Evidence**: RUNTIME, GREP

### What is wrong

[`mac/Bridge/Sources/Bridge/BridgeApp.swift:19`](../mac/Bridge/Sources/Bridge/BridgeApp.swift#L19)
declares `MenuBarExtra { StatusPanel(...) }` with no `.menuBarExtraStyle(.window)`. The
default style is `.menu`, so SwiftUI renders the whole panel as a real `NSMenu`.

Accessibility enumeration of the live app returned 22 flat menu items, 18 of them disabled:

```
[false] Bridge
[false] SM-S931B
[false] Paired with SM-S931B
[true ] Send File…
[false] Drag a file onto this menu to send it to your phone.
[false] Permissions
[false] Bluetooth
[false] missing value      ← the Circle() status dot, promoted to its own menu item
[false] Granted
[false] Local Network
[false] missing value
[false] Not Requested
[true ] Request
[false] Notifications
[false] missing value
[false] Granted
[true ] Unpair
[true ] Quit Bridge
```

### Consequences, all from this one cause

1. **Permission rows are shredded into three menu items each.** `HStack { Circle(); Text(name); Spacer(); Text(status) }` cannot survive NSMenu flattening — the coloured dot becomes a blank item between the name and the status.
2. **Every non-Button view renders as disabled grey text.** `Send File…` reports `enabled = true` but reads as disabled, because it sits among 18 genuinely-disabled items.
3. **`.sheet` cannot present from an NSMenu.** `PairPromptView` is not merely hidden until the popover opens — it is structurally unreachable. This is the root cause behind AUD-D's auto-accept.
4. **`.dropDestination` does nothing on an NSMenu.** The line *"Drag a file onto this menu to send it to your phone."* instructs the user to do something that cannot work.
5. **Width is NSMenu-driven**, producing the ragged layout.

### Fix

Add `.menuBarExtraStyle(.window)` to the `MenuBarExtra` scene, then re-lay out `StatusPanel`
for a real popover: fixed `.frame(width: 260)`, `.padding(12)`, fewer dividers, and
permission rows filtered to `status != .granted`.

### Done when

- [ ] The panel renders as a popover with intact rows (dot, name, status on one line)
- [ ] Dragging a file onto the open panel sends it to the phone
- [ ] A pair confirmation sheet is visible when one is pending
- [ ] `Send File…` is visually distinguishable from the labels around it

## AUD-B — The link state lies in three different ways

**Severity**: High · **Platform**: both · **Evidence**: RUNTIME, GREP, SOURCE

### B1 — `LinkHealth` is dead code

[`mac/Bridge/Sources/Bridge/BLE/LinkHealth.swift`](../mac/Bridge/Sources/Bridge/BLE/LinkHealth.swift)
defines `.stale(seconds:)`, `.dead`, `.outOfRange` and a `guidance(for:)` carrying the
correct copy — *"The phone's Bridge service may have been stopped by battery management.
Open Bridge on the phone to restart."*

`grep -rn "LinkHealth\|linkHealth" mac/Bridge/Sources/` returns **zero hits outside the file
itself**. It is wired to nothing. `StatusPanel` and `menuBarIcon` both switch on the
four-case `LinkState` only.

The PRD names this the failure mode that matters most: *"Every one of these presents to the
user as nothing happening."*

### B2 — "Out of range" is shown for a phone on the desk — RUNTIME

Force-stopping `com.bridge.app` on a phone 30 cm from the Mac on a USB cable produced:

```
[false] Out of range
[false] Last seen: just now
```

The Mac blames distance for a killed service. `LinkState.connecting → "Out of range"` in
[`StatusPanel.swift:57`](../mac/Bridge/Sources/Bridge/UI/StatusPanel.swift#L57) labels three
distinct conditions (negotiating, trust failed, service dead) with a fourth condition's
name — and that fourth is the only reassuring one.

### B3 — Up to 120 seconds of stale "Connected"

[`PingWatchdog.swift:17`](../mac/Bridge/Sources/Bridge/Protocol/PingWatchdog.swift#L17):

```swift
init(pingInterval: TimeInterval = 30, watchdogTimeout: TimeInterval = 90)
```

90-second timeout, evaluated only on a 30-second tick. On a *silent* drop (phone out of BLE
range, One UI kills the process, radio glitch — no clean socket close) the Mac shows
"Connected" with a live battery percentage for up to two minutes.

A clean close is handled correctly; this is the silent path only.

### B4 — Every send reports success

[`BLEManager.swift:95`](../mac/Bridge/Sources/Bridge/BLE/BLEManager.swift#L95):

```swift
func sendPacket(_ packet: BridgePacket) -> Bool {
    guard let channel = l2capChannel else { return false }
    channel.send(packet)      // returns Void, swallows all errors
    return true
}
```

Returns `true` whenever the channel *object* exists. During the B3 window every notification
reply reports success, so `NotificationManager.postDeliveryFailure()` — *"Reply could not be
delivered / Phone is out of range"* — can essentially never fire for the case it was
written for.

### B5 — "Connected" means two different things

[`BLEManager.swift:440`](../mac/Bridge/Sources/Bridge/BLE/BLEManager.swift#L440) transitions
to `.connected` the instant the L2CAP channel opens — before identity, before pairing,
before any trust check.

[`LinkState.kt`](../android/Bridge/app/src/main/java/com/bridge/app/LinkState.kt) refuses to
say `CONNECTED` unless `isVerified`, documenting why: *"A socket to an untrusted peer
delivers nothing."*

Same word, two screens, and the Mac's is the dishonest one.

### Fix

Publish `LinkHealth` off `BLEManager` (its evaluator already takes `lastSeen`,
`bleConnected`, `bluetoothOn` — all three exist) and make it what `StatusPanel` and
`menuBarIcon` switch on. Render `guidance(for:)` as the panel's one line of body text.
Make `sendPacket` return real success. Gate the Mac's `.connected` on verification, as
Android already does. Lower the watchdog timeout, or add a `.stale` state before `.dead`.

### Done when

- [ ] Killing the phone service shows "Not responding" with the restart guidance, not "Out of range"
- [ ] Walking the phone out of BLE range shows "Out of range"
- [ ] A reply sent into a dead link posts the delivery-failure notification
- [ ] The Mac does not say "Connected" before the peer is verified

## AUD-C — No transport security, and pre-identity packets are accepted

**Severity**: Critical · **Platform**: both · **Evidence**: GREP, DOC, SOURCE

### C1 — There is no TLS anywhere

| Source | Claim |
|---|---|
| `README.md` | "everything is mutually authenticated TLS" |
| `.claude/CLAUDE.md` | "mutual TLS with pinned certs" |
| `openspec/specs/security/certificate-pinning/spec.md` | A shipped requirement **"Mutual TLS over L2CAP"** with three scenarios |

Reality: [`TLSWrapper.swift`](../mac/Bridge/Sources/Bridge/Security/TLSWrapper.swift) has zero
callers (only its own definition and four `project.pbxproj` references).
`CertificateManager.createSSLContext()`
([`CertificateManager.kt:63`](../android/Bridge/app/src/main/java/com/bridge/security/CertificateManager.kt#L63))
has zero callers. Both are dead code.

The control channel is plaintext newline-delimited JSON. File payloads are plaintext TCP.
Certificates are generated, fingerprints exchanged and pinned — but the pin never
authenticates a channel. It is a name tag, not a lock.

### C2 — Any packet is accepted from an unidentified peer

[`L2capServer.kt:198`](../android/Bridge/app/src/main/java/com/bridge/ble/L2capServer.kt#L198):

```kotlin
if (peerDeviceId != null && peerFingerprint != null) {
    val trusted = TrustStore.getInstance().isTrusted(peerDeviceId!!, peerFingerprint!!)
    if (!trusted && packet.type != "bridge.identity" && packet.type != "bridge.pair") {
        Log.w(TAG, "Dropping packet from untrusted device: ${packet.type}")
        return
    }
}
```

Before an identity packet arrives both fields are null, so the guard is skipped entirely and
**every packet type is processed from a totally unidentified peer** — clipboard writes,
notification replies, file-transfer requests.

The spec says the opposite: *"only `bridge.identity` and `bridge.pair` packets are accepted;
all other packets are dropped."*

### C3 — The trust check fails open

`catch (_: IllegalStateException) {}` around that same check. If `TrustStore` is not
initialised, the exception is swallowed and the packet is processed.

### C4 — Unbounded `readLine()`

[`L2capServer.kt:122`](../android/Bridge/app/src/main/java/com/bridge/ble/L2capServer.kt#L122)
reads lines with no maximum length, at a pre-auth trust boundary. Bytes with no newline grow
a `String` until OOM.

### Fix

Either implement the specced mutual TLS on both sides (wire the two dead classes), or amend
the README, PRD, CLAUDE.md and the security spec to describe what actually ships — but do
not leave four documents describing an app that does not exist. Independently of that
decision: invert C2 so the default is *drop* until identity is known, remove the fail-open
catch, and cap line length.

### Done when

- [ ] A peer that has sent no identity packet cannot get any packet type processed
- [ ] An uninitialised trust store drops packets rather than passing them
- [ ] A line over the cap closes the connection instead of growing
- [ ] Docs and specs match the shipped transport, whichever way it lands

## AUD-D — Pairing has no human gate

**Severity**: Critical · **Platform**: both · **Evidence**: GREP, DOC, SOURCE

### D1 — The six-digit verification code was never built

The PRD specifies it in detail: both devices independently derive a six-digit code from the
two certificate fingerprints — sorted, concatenated, hashed, reduced — display it, and the
user confirms the digits match before either side pins. *"Acceptance is **not** automatic."*
The spec softens this to *"user confirmation on both sides"*.

`grep -rn "verificationCode\|sixDigit\|verifyCode\|pairCode"` across the repo returns **zero
hits**. It is in neither the spec's requirements nor the code.

### D2 — Android auto-accepts every pair request

[`L2capServer.kt:98`](../android/Bridge/app/src/main/java/com/bridge/ble/L2capServer.kt#L98):

```kotlin
pm.onPairRequest = { deviceName, fingerprint ->
    Log.i(TAG, "Auto-accepting pair request from $deviceName (fp: $fingerprint)")
    pm.acceptPair()
}
```

Unconditional. There is no Android UI for a pair prompt at all.

### D3 — The Mac auto-accepts on an empty trust store

[`PairingManager.swift:190`](../mac/Bridge/Sources/Bridge/Security/PairingManager.swift#L190)
calls `presentPairConfirmation(...)` and then `acceptIncomingPair()` immediately — it shows
the sheet *and* accepts, so the sheet is theatre. The comment concedes why: *"the prompt only
renders while the menu-bar panel happens to be open."* See AUD-A; that is fixable.

`PairPromptView`'s 30-second "Auto-reject in Ns" countdown only runs while the view is on
screen, so the stated timeout is also fiction.

### D4 — A changed fingerprint triggers re-pair, not refusal

PRD: *"a connection whose presented certificate does not match the pinned fingerprint is
closed rather than re-paired — a changed fingerprint means a reinstall or an impostor, and
both require a deliberate re-pair."*

Android calls `requestPair()` instead
([`PairingManager.kt:70`](../android/Bridge/app/src/main/java/com/bridge/security/PairingManager.kt#L70)),
and with D2 that request is auto-accepted at the other end. The Mac stages a prompt that
AUD-A makes invisible.

### D5 — No device picker

PRD: *"the Mac does not auto-connect to the first advertiser it sees... presents the
discovered devices by name and signal strength and the user picks one."*

[`BLEManager.swift:292`](../mac/Bridge/Sources/Bridge/BLE/BLEManager.swift#L292) logs the
RSSI and then calls `connectToPeripheral(peripheral)` immediately. There is a single
`discoveredPeripheral` slot. The README already concedes the behaviour: *"the Mac may
reconnect to whichever device advertises first."*

### Why D1–D5 are one item

They compound. No transport encryption (AUD-C), no pre-identity packet filter (C2), no
pairing confirmation (D2/D3), and no picker (D5) together mean anything in BLE range can
pair itself and inject packets without a human touching either screen. Each alone is
survivable at one metre; together they are not. Fix as one change, not five.

### Done when

- [ ] Both screens show the same six digits before anything is pinned
- [ ] Declining on either side leaves both trust stores unchanged
- [ ] A fingerprint that does not match the pin closes the connection and requires a deliberate re-pair
- [ ] An unpaired Mac lists discovered phones by name and RSSI and waits for a choice

## AUD-E — File transfer accepts anything from anyone

**Severity**: High · **Platform**: both · **Evidence**: SOURCE

### E1 — Path traversal on receive

[`FileReceiveController.swift`](../mac/Bridge/Sources/Bridge/FileTransfer/FileReceiveController.swift):
`safeName` is the peer's filename, unsanitised, passed to
`downloads.appendingPathComponent(safeName)`. A filename of `../../.zshenv` escapes
`~/Downloads`. `safeName` only guards against the empty string.

[`FileReceiver.kt`](../android/Bridge/app/src/main/java/com/bridge/filetransfer/FileReceiver.kt)
passes the same unsanitised filename to `MediaStore.Downloads.DISPLAY_NAME`.

### E2 — No size cap

The sender declares `payloadSize`; the receiver writes exactly that many bytes. Nothing
bounds it. A buggy or hostile peer fills the disk.

### E3 — The payload server serves the first connection that arrives

[`PayloadServer.kt`](../android/Bridge/app/src/main/java/com/bridge/filetransfer/PayloadServer.kt)
binds an ephemeral port with no auth and no TLS, and its own doc comment says it *"streams
the payload to the first connection that arrives"*. On Tier 3 (Wi-Fi LAN) any host on the
network that reaches that port inside the window gets the file.

### E4 — No consent step

Both sides write incoming files silently — the Mac to `~/Downloads`, the phone to
`MediaStore.Downloads`. AirDrop asks. Quick Share asks. Combined with C2 (unauthenticated
injection) and E1, silent-accept is the wrong default.

Receive failures on the Mac are logged only; the user is told nothing.

### Fix

Sanitise to a basename and reject separators. Cap `payloadSize` and reject over it. Require
the payload connection to come from the paired peer's address, or carry a one-time token
from the control channel. Notify before writing, with a Decline. Surface receive failures.

### Done when

- [ ] A `../` filename lands inside Downloads with a flattened name, or is refused
- [ ] A payload declaring an absurd size is refused before any bytes are written
- [ ] A connection to the payload port from an unrelated LAN host gets nothing
- [ ] An incoming file is announced before it is written, with a way to decline
- [ ] A failed receive tells the user

## AUD-F — Notification mirroring is broken in four ways

**Severity**: High · **Platform**: both · **Evidence**: RUNTIME, GREP, SOURCE

### F1 — Dismissing on the phone leaves a ghost on the Mac

`BridgePacket.notificationRequest()` exists on Android
([`BridgePacket.kt:148`](../android/Bridge/app/src/main/java/com/bridge/protocol/BridgePacket.kt#L148))
and has **zero callers**. `onNotificationRemoved` only cleans the reply cache.

Mac → phone works (dismiss on Mac cancels on phone). The reverse does not. Every message you
read on your phone leaves a stale notification on the Mac. This is the one that will annoy
you daily.

### F2 — Reply from the Mac works exactly once

[`BridgeNotificationListener.kt:34`](../android/Bridge/app/src/main/java/com/bridge/notifications/BridgeNotificationListener.kt#L34):

```kotlin
fun getCachedAction(requestReplyId: String): CachedReplyAction? {
    return synchronized(replyCache) { replyCache.remove(requestReplyId) }
}
```

`remove`, not `get`. The second reply to the same notification is a cache miss and is
silently dropped. There is no ack packet, so with AUD-B4 the Mac reports success.

### F3 — Deny-by-default with a discovery-seeded list means nothing mirrors — RUNTIME

[`NotificationFilter.kt`](../android/Bridge/app/src/main/java/com/bridge/notifications/NotificationFilter.kt):
`shouldForward(pkg) = !masterMute && pkg in allowed`, and apps only enter the list *after*
they have posted a notification.

Day one: empty list, zero notifications mirrored, and nothing on either home screen says so.
**On the test phone right now every toggle is off.** The headline feature is doing nothing.

### F4 — The app list shows raw package names — RUNTIME

Observed on device: `com.amazon.mp3`, `com.application.zomato`,
`com.application.zomato.district`, `com.axis.mobile`, `com.bigbasket.mobileapp`,
`com.bt.bms`, `com.dreamplug.androidapp`. Only *Amazon* and *Android System* resolved to a
label and icon.

`getApplicationLabel()` is failing for nearly every app — Android 11+ package visibility
requires a `<queries>` block in the manifest. Users cannot identify which app a row is, which
makes F3 unfixable by the user even once they find the screen.

Rows are also enormous (eight fill a 2340px screen), long names wrap mid-word
(`com.application.zomato.di` / `strict`), and the last row clips.

### Fix

Send `bridge.notification.request` from `onNotificationRemoved`. Change `remove` to `get` and
evict on `onNotificationRemoved` only. Add `<queries>` to the manifest. Reconsider
deny-by-default, and surface the enabled count on both home screens
(`Notifications · Mirroring 3 apps` / `· Paused` / `· No apps on yet`). Tighten row height.

### Done when

- [ ] Clearing a notification on the phone clears it on the Mac
- [ ] Two consecutive replies to one notification both arrive
- [ ] Every row shows an app name and icon
- [ ] Both home screens state how many apps are mirroring
- [ ] A fresh install either mirrors something, or says plainly that it will not

## AUD-G — Clipboard burns battery, leaks on focus, and ignores the size rule

**Severity**: Medium · **Platform**: android · **Evidence**: RUNTIME, SOURCE

### G1 — A 2 Hz poll that can never succeed

[`ClipboardBridge.kt:51`](../android/Bridge/app/src/main/java/com/bridge/clipboard/ClipboardBridge.kt#L51)
posts `pollRunnable` every 500 ms on the main thread, forever. Android 16 blocks background
clipboard reads, so `getCurrentClipText()` returns null every time.

`hasBackgroundClipboardAccess` is computed, logged once at `start()`, and **never gates
anything**. Pure battery burn, against the PRD's own *"Bluetooth battery drain → tool gets
uninstalled"* risk row.

### G2 — Opening the app silently sends your clipboard — RUNTIME

A **"Copied."** toast fired on the home screen without anything being tapped —
`onWindowFocusChanged` → `sendClipboardFromActivity()`. Merely opening the app ships whatever
is on your clipboard to the Mac and tells you afterwards.

The word is also wrong: nothing was copied, something was *sent*.

### G3 — The 10 KB rule is not honoured

The PRD and CLAUDE.md both require payloads over 10 KB to use out-of-band transfer. Clipboard
sends unbounded text as one JSON line over a 50–100 KB/s BLE link, blocking the control
channel for minutes on a large clip.

### G4 — The card is permanently orange — RUNTIME

`updateClipboardStatus()` hard-codes two lines and `Color.parseColor("#FF9800")` in Kotlin,
not `strings.xml`. Same text and same warning colour whether or not anything is wrong, and
the `→` arrows read as engineer's shorthand. Permanent amber is wallpaper; when it should
warn, it will not register.

### Fix

Gate `start()` on `hasBackgroundClipboardAccess` and stop the poll when it is false. Make the
focus send explicit, or at minimum announce it before it happens with honest wording. Cap
clipboard payload and route the overflow out of band, or truncate and say so. Make the status
line reflect reality (`Last synced 2 min ago`) and move the strings into `strings.xml`.

### Done when

- [ ] No clipboard polling occurs when background access is denied
- [ ] Opening the app does not send the clipboard without the user asking
- [ ] A clip over the cap does not block the control channel
- [ ] The clipboard card changes with state and is amber only when something is wrong

## AUD-H — There is no off switch

**Severity**: High · **Platform**: both · **Evidence**: RUNTIME, GREP

`BLEManager.disconnect()` exists at
[`BLEManager.swift:80`](../mac/Bridge/Sources/Bridge/BLE/BLEManager.swift#L80) and has **zero
callers**.

Android has one menu item. Live accessibility dump of the Mac menu ends `Unpair` / `Quit
Bridge`. `stopSelf()` is never called in `BridgeService`, so the foreground service cannot be
stopped from inside the app — the README's answer to "unpair on Android" is *uninstall*.

| Want | Mac | Android |
|---|---|---|
| Stop the link for an hour | ✗ | ✗ |
| Stop sharing, keep the pairing | ✗ | ✗ |
| Forget this device | Unpair | **uninstall** |
| Kill it entirely | Quit Bridge | force-stop |

The middle is missing. There is no way to say "not right now" — only destroy the trust
relationship or kill the process. Meanwhile the phone streams notifications and clipboard to
whatever Mac is in range, permanently.

Related: the Android toolbar's single action renders as **"CONNECTED"** when connected
(`actionLabel(CONNECTED)` returns `"Connected"`), sitting 200 px from a green pill saying the
same word, and `onConnectAction()` for that state is `LinkState.CONNECTED -> Unit`. A button
that does nothing, styled as a button, duplicating the pill.

### Fix

Add **Disconnect** to both sides — drop the socket and stop advertising, keep the pin, stay
down until the user reconnects. Add **Unpair** to Android. Wire the Mac's existing
`disconnect()`. Replace the dead "CONNECTED" toolbar item with Disconnect when connected.

### Done when

- [ ] Disconnect on either side drops the link on both and the pin survives
- [ ] Reconnect restores the link with no re-pairing
- [ ] Android can forget the Mac without uninstalling
- [ ] No control in either app is labelled with a status

## AUD-I — Android screens are a status dump

**Severity**: Medium · **Platform**: android · **Evidence**: RUNTIME, GREP

### I1 — Permissions render as a monospace text blob

[`MainActivity.kt`](../android/Bridge/app/src/main/java/com/bridge/app/MainActivity.kt):

```kotlin
permissionStatus.text = checker.all().joinToString("\n") { "${it.name}: ${it.status.label}" }
```

On screen: `Notification Access: Granted` / `Battery Optimization: Granted` / `ADB Clipboard:
Limited`. It reads like log output.

`PermissionItem.detail` has **zero references** — and for the ADB clipboard grant that field
holds *the actual command the user must run*. Status vocabulary is incoherent:
`GRANTED`→"Granted", `DENIED`→"Disabled", `LIMITED`→"Limited". Three statuses, three
unrelated words, none saying what to do.

### I2 — A modal on every app open

`maybePromptLinkIssue()` fires from `onResume` whenever the link is anything but perfect,
saying for the fourth time on one screen what the pill, the device line and the toolbar
action already say. "Not now" implies it will not return; it returns every resume.

### I3 — Denied permissions are a dead end

Deny any runtime permission and the only feedback is `macName.text = "Permissions required to
run Bridge"`, overwriting the device-name line. There is no retry button anywhere in the app.
The user must find system settings unprompted, or uninstall.

### I4 — Wasted space

`app_glyph` is a 56 dp copy of the launcher icon shown to a user who is already inside the
app, eating the card's left third.

### Fix

Three tappable permission rows — dot, name, one line of consequence, trailing action — hidden
when granted and not ongoing. Surface `detail` for the adb grant with a copy-command action.
Delete the resume modal and move `promptBody` inline under the state. Make the denied path
recoverable with a "Grant permissions" button falling back to app settings. Drop `app_glyph`.

### Done when

- [ ] Each permission row states its consequence and offers its own action
- [ ] The adb command is reachable from the UI
- [ ] Opening the app with a broken link shows no modal
- [ ] A user who denies a permission can grant it later without leaving the app

## AUD-J — Mac panel content and accessibility

**Severity**: Medium · **Platform**: mac · **Evidence**: RUNTIME, GREP

### J1 — The Local Network permission row is a permanent lie

`PermissionChecker.setLocalNetwork(_:)` has **zero callers**. `localNetworkStatus` stays
`.notRequested` forever, so the row renders as a yellow dot, "Not Requested", and a "Request"
button that only opens System Settings. Confirmed live.

This is the permission gating Wi-Fi file transfer — the one row a user checks when a transfer
fails. A permanent yellow dot also trains the user to ignore the honest rows.

### J2 — The menu bar item has no accessible name

Connected, its AX title is `"25%"`. Disconnected, it resolved to **`"Mobile Data"`** — a
neighbouring menu bar item, because the label collapses to a bare icon with no text.
VoiceOver gets nonsense either way.

### J3 — Two battery percentages, no disambiguation

The menu bar shows `🔗 25%` two icons away from macOS's own battery indicator. Nothing says
which phone or which battery.

### J4 — The device name is a model number, printed twice

The status line says `SM-S931B`; the line under it says `Paired with SM-S931B`. Android sends
`Build.MODEL` as `deviceName`, and there is no rename field anywhere. The PRD asks for *"a
user-visible deviceName"*. Harmless with one device, unusable once AUD-D5 adds a picker.

### J5 — The menu bar label jitters

The label is an `HStack` conditionally containing up to five elements (state icon, pair
badge, permission triangle, battery glyph, percentage). Width changes whenever any flips,
shoving every item to its left.

### Fix

Call `setLocalNetwork` from the first `NWBrowser`/`NWListener` result path, or delete the row
— there is no TCC query API, so observing a failed browse is the only honest signal. Give the
menu bar item an explicit accessibility label. Fix the composition to a constant width. Show
the device name once. Add a rename field, or label the battery as the phone's.

### Done when

- [ ] The Local Network row reports a real status or is gone
- [ ] VoiceOver announces something meaningful for the menu bar item
- [ ] The menu bar item does not change width as state changes
- [ ] The device name appears once

## AUD-K — Protocol and process debt

**Severity**: Low–Medium · **Platform**: both, protocol · **Evidence**: GREP, DOC

### K1 — Capabilities and `protocolVersion` are write-only

Both are sent in every identity packet and **never read** on either side. The PRD says
*"Capability arrays, not the version number, decide what a peer may send."*

Distribution is `brew upgrade` on the Mac plus a manual APK sideload on the phone, so version
skew is the *normal* state — and nothing detects it or tells the user.

### K2 — `protocol/constants.json` is incomplete

It omits the RFCOMM file-transfer UUID `A76E1A03-…`, which both sides hardcode separately.
The shared-constants file does not hold all the shared constants.

### K3 — Spec rot

[`openspec/specs/ble-transport/discovery/spec.md:9`](../openspec/specs/ble-transport/discovery/spec.md#L9)
carries a corrupted UUID: `a]76e1a0-b]5d-4]3c-8]2b-d]0e9f8a7b6c5`. Cosmetic, but it is in the
folder that is supposed to be shipped truth.

### K4 — Dead, broken helper

`BridgeNotificationListener.isListenerEnabled()`
([line 38](../android/Bridge/app/src/main/java/com/bridge/notifications/BridgeNotificationListener.kt#L38))
passes `null` as the `ContentResolver` to `Settings.Secure.getString`. Zero callers;
`MainActivity` has its own correct copy. Delete it.

### K5 — PRD goal 5 is partly unbuilt and uncut

*"Phone battery, signal and Do Not Disturb state visible on the Mac."* Only battery shipped.
`grep -i "signalStrength|doNotDisturb|INTERRUPTION_FILTER"` returns nothing across both apps.
Signal and DND are not built, not cut in writing, and not in the backlog — so goal 5 silently
reads as done.

### K6 — The specs describe behaviour that was never built

`openspec/specs/` is the "already shipped" location, and it contains a full *Mutual TLS over
L2CAP* requirement (AUD-C1) and a *"user confirmation on both sides"* pairing requirement
(AUD-D1), neither of which exists in code. Something synced or archived specs without the
code matching.

**This one is worth a look at the process, not just the artifact** — the same gap can reopen
on the next iteration. Candidate: an `openspec validate` step that fails when a spec scenario
has no corresponding test or implementation reference.

### Done when

- [ ] A version- or capability-mismatched peer is detected and surfaced
- [ ] `constants.json` holds every shared constant, and both sides read it
- [ ] The discovery spec's UUID matches `constants.json`
- [ ] Goal 5 is either built or recorded as cut
- [ ] A spec requirement cannot reach `openspec/specs/` without matching code

## The highest-value thing nobody has built

**Wi-Fi LAN as a control fallback.** The PRD's own analysis — the "bottom-right quadrant" —
says Tier 3 should carry notifications and clipboard when BLE is out of range but both
devices share a network: *"there is no reason for Bridge to go dark"*, and *"this costs
almost nothing, because tier 3 has to exist for files anyway."*

The code does Tier 3 for files only. Nothing in the backlog. This is the highest-value
unbuilt item in the PRD and the transport is already paid for. Not filed as an AUD item
because it is a feature, not a defect — raise it as its own backlog entry if wanted.

## What this audit did not do

- No fixes, no commits beyond this doc and its backlog rows.
- The Android APK was **not** rebuilt — findings F4, G2, I1 and H's toolbar item come from the build already installed on the phone. If the working tree has uncommitted Android changes, re-verify against `HEAD`.
- The silent-drop path (AUD-B3) was not stopwatched end-to-end; the 90 s / 120 s window is read from the watchdog constants and the `sendPacket` return, not measured by carrying the phone out of range.
- File transfer and notification mirroring were not exercised in flight — AUD-E and AUD-F1/F2 are SOURCE-class, not RUNTIME.
- No unit or instrumentation tests were run. `xcodebuild … build` succeeded; `xcodebuild test` and `gradlew test` were not run.
